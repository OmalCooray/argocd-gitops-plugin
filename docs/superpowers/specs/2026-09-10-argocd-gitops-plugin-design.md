# ArgoCD GitOps Plugin — Design

**Date:** 2026-09-10
**Status:** Approved (design phase)
**Author:** Omal Cooray (with Claude)

## Summary

Build a Claude Code **plugin** (`argocd-gitops-plugin`) that automates the full
lifecycle of running applications on Argo CD via GitOps:

- installing/bootstrapping Argo CD on any Kubernetes cluster,
- onboarding upstream Helm charts into a Git "catalog",
- deploying catalog apps to specific clusters/environments,
- promoting changes between environments,
- reviewing `values.yaml` for dev-readiness / prod-readiness,
- troubleshooting deployed applications (live or offline),
- doing the Git plumbing (repo creation, branches, PRs, PR review).

Once the plugin exists, it is used to generate a second repo: a restructured
Argo CD GitOps config repo modeled on the user's existing
`data-platform-k8s-configs` (folder-per-app wrapper charts + Argo CD
`Application` manifests).

**Build order:** plugin first (this repo, `C:\claude\argocd-gitops-plugin`),
GitOps config repo second (generated by the plugin).

## Background

The user has previously built an Argo CD repo by hand (`data-platform-k8s-configs`)
with this per-app layout:

```
<app>/
  Chart.yaml     # umbrella chart; upstream chart pinned as a dependency
  values.yaml    # overrides for the upstream chart
  <app>.yaml     # Argo CD Application manifest
```

Applications were reconciled with a hand-written bash script that diffed
`applications.txt` against `kubectl get applications` and `kubectl apply`-ed the
missing ones. Pain points the user wants solved:

1. Manual `kubectl apply` per app; no self-healing list of apps.
2. No bootstrap story for Argo CD itself.
3. No multi-environment support (dev/prod).
4. Manual secrets handling.
5. No structured way to review configs or troubleshoot running apps.

## Goals

- A reusable, installable Claude Code plugin — not repo-local scripts.
- CLI-first: depends on `git`, `gh`, `kubectl`, `helm`, `argocd`. No bundled MCP
  servers; Argo CD MCP documented as optional.
- Reproduce the user's wrapper-chart style so generated files match hand-written ones.
- App-of-apps ("root application") replaces the reconcile script.
- Repo structure that makes multi-environment and secrets **additive** later,
  without restructuring.
- Agents for the multi-step flows (onboarding a new app, iterative troubleshooting).

## Non-Goals

- Not building an Argo CD MCP server (may adopt Akuity's later).
- Not managing cluster provisioning (Terraform/infra is out of scope).
- Not a general Kubernetes plugin — scoped to Argo CD + Helm GitOps.
- Phase 3 (multi-env, secrets) is designed for but not the initial build target.

## Target GitOps repo structure (what the plugin generates)

```
<gitops-repo>/
├── charts/                       # CATALOG — wrapper charts; deploys nothing itself
│   └── <app>/
│       ├── Chart.yaml            # umbrella chart; upstream chart pinned as dependency
│       └── values.yaml           # base, environment-agnostic overrides
│
├── environments/
│   └── <env>/                    # one folder per cluster/environment
│       ├── root.yaml             # root Application → syncs this folder's apps/
│       ├── apps/
│       │   └── <app>.yaml        # Argo CD Application; only apps wanted on THIS cluster
│       └── values/
│           └── <app>.yaml        # optional per-env Helm values overlay
│
├── bootstrap/
│   └── install.sh                # helm install argo-cd + kubectl apply <env>/root.yaml
│
├── .claude/
│   └── CLAUDE.md                 # repo facts: repo URL, cluster names, argocd ns,
│                                 # catalog inventory, pointer to the plugin
├── CODEOWNERS                    # environments/prod/** → platform leads
└── README.md
```

### Key conventions

- **Catalog vs deployment set are separate.** A `charts/<app>/` folder is just
  available config; nothing deploys until an `Application` in some
  `environments/<env>/apps/` references it.
- **Application manifests** use a multi-source spec: source 1 = `charts/<app>/`
  (the wrapper chart), source 2 = `environments/<env>/values/<app>.yaml` as an
  extra Helm values file (referenced via `$values`). Sync policy: automated,
  `prune: true`, `selfHeal: true`, `CreateNamespace=true`.
- **Environment tracking model:**
  - `environments/dev/apps/*.yaml` → `targetRevision: master` (auto-syncs on merge)
  - `environments/prod/apps/*.yaml` → `targetRevision: <pinned SHA or prod-* tag>`
    (moves only via an explicit PR that bumps the pin)
- **Branching:** one long-lived branch (`master`); environments are directories,
  not branches. Promotion = a PR editing `environments/<target>/values/*` or
  bumping the target env's `targetRevision`. Branch-per-environment is explicitly
  rejected (promotion-by-merge drags unrelated changes; env diffs become
  permanent merge conflicts; no shared chart base; no read isolation anyway).
- **Read isolation:** single repo. `values.yaml` carry no secrets (those go
  through External Secrets / Sealed Secrets in Phase 3), so shared read access is
  acceptable; write control on prod is via `CODEOWNERS` + branch protection.

### Migration from the existing repo

Each existing `<app>/` folder splits: `Chart.yaml` + `values.yaml` →
`charts/<app>/`; `<app>.yaml` → `environments/data-platform/apps/<app>.yaml`.
`applications.txt` and the reconcile script are deleted (root app replaces them).

### Skills (knowledge loaded on demand)

| Skill | Purpose |
|---|---|
| `argocd-repo-conventions` | The repo layout above, naming rules, manifest templates, how sources + values wire together, the dev/prod tracking model. Loaded before generating any file. |
| `helm-chart-onboarding` | Find a chart (`helm repo add`/`search repo`, ArtifactHub REST via WebFetch), pick + pin a version, pull upstream `values.yaml` (`helm show values`), produce a minimal override. |
| `values-review` | Rubric for dev-ready vs prod-ready values. Best-practice defaults, editable in the skill. Checks: resource requests/limits, replicas ≥ 2 + PDB, liveness/readiness/startup probes, `securityContext`/non-root, persistence + real StorageClass, anti-affinity, HPA where supported, no floating image tags, backups for stateful apps, no plaintext secrets. |
| `argocd-troubleshooting` | How to read sync/health status; common failure signatures (hook failure, CRD ordering, image pull, OOMKill, bad values path, namespace missing, chart version drift) and their fixes. |

### Commands (workflows)

| Command | Output / behavior |
|---|---|
| `/argocd-init-repo <name>` | Scaffold a new GitOps repo (full tree, `README`, `.claude/CLAUDE.md`, `CODEOWNERS`), `gh repo create`, initial push. |
| `/argocd-add-chart <name> [version]` | Research chart → scaffold `charts/<name>/` (`Chart.yaml` w/ pinned dependency + starter `values.yaml`) → branch + PR. Does not deploy. |
| `/argocd-deploy <app> <env>` | Generate `environments/<env>/apps/<app>.yaml` (+ optional values overlay) → branch + PR. |
| `/argocd-promote <app> <from-env> <to-env>` | Diff the two envs' values files, generate a target-env-adjusted change (or bump `targetRevision`) → branch + PR. |
| `/argocd-add-env <name>` | Scaffold `environments/<name>/` with `root.yaml`. |
| `/argocd-bootstrap [kube-context]` | Generate/refresh `bootstrap/install.sh` for a target cluster. |
| `/argocd-audit [env]` | Read-only. Diff `environments/<env>/apps/` against live `argocd app list` / `kubectl get applications`; report drift. (Replaces the old reconcile script's useful half.) |
| `/argocd-doctor [app]` | Diagnose a degraded / OutOfSync app; propose a fix. Live mode (cluster access) or offline mode (paste `argocd app get -o yaml` / `kubectl` dumps). |
| `/argocd-review-values <app> [--profile dev\|prod]` | Run the `values-review` rubric; optionally emit a `values-<profile>.yaml` overlay. |
| `/argocd-review-pr <n>` | Fetch PR diff; run `argocd-repo-conventions` checks + `values-review` rubric + `helm template` lint; post a review summary via `gh`. |

### Agents

| Agent | Role |
|---|---|
| `argocd-onboarder` | Full "new app" flow end to end: research chart → scaffold catalog entry → deploy to an env → open PR. Kept off the main thread. |
| `argocd-doctor` | Iterative live troubleshooting: query Argo CD / `kubectl`, drill into degraded resources, propose a fix, and (only with user approval) apply it via a PR. Uses `mcp__argocd__*` tools if present, else the `argocd` CLI. |

### Git integration

All via `git` + `gh` CLI. The GitHub MCP server is **not** required (it failed
auth during design; `gh` is the reliable path — user authenticates it once).

- **Create repo:** `/argocd-init-repo` → `gh repo create` + push.
- **Commit:** every scaffold/deploy command works on a short-lived branch, never
  commits to `master`.
- **Open PR:** `gh pr create` with a templated body (chart, version, target env,
  `helm template` diff preview).
- **Review PR:** `/argocd-review-pr <n>` posts a structured review.

### MCP posture

- **Bundled MCP servers: none.** Keeps the plugin installable with zero MCP setup.
- **`.mcp.json` ships with the Akuity Argo CD MCP server defined but disabled**,
  plus README instructions to enable it. Worthwhile only for deep interactive
  troubleshooting via the `argocd-doctor` agent.
- Skills/agents are written "use `mcp__argocd__*` if available, otherwise shell
  out to `argocd`".

### Plugin dependencies (documented in README)

`git`, `gh` (authenticated), `kubectl`, `helm`, `argocd`. Standard tooling for
anyone already operating Argo CD.

## Phasing

### Phase 1 — usable core
- Plugin scaffold (`plugin.json`, README, templates).
- Skills: `argocd-repo-conventions`, `helm-chart-onboarding`.
- Commands: `/argocd-init-repo`, `/argocd-add-chart`, `/argocd-deploy`,
  `/argocd-bootstrap`, `/argocd-audit`.
- Agent: `argocd-onboarder`.
- Git: branch + PR flow via `gh`.
- **Exit criterion:** from an empty cluster, `/argocd-init-repo` +
  `/argocd-bootstrap` + `/argocd-add-chart` + `/argocd-deploy` produces a repo
  whose root app syncs a Helm chart onto the cluster.

### Phase 2 — review & operate
- Skill: `values-review`, `argocd-troubleshooting`.
- Commands: `/argocd-review-values`, `/argocd-review-pr`, `/argocd-doctor`.
- Agent: `argocd-doctor` (live cluster access; offline fallback).

### Phase 3 — multi-env & secrets
- Commands: `/argocd-add-env`, `/argocd-promote`.
- prod SHA-pinning + `CODEOWNERS` enforcement.
- Secrets convention: External Secrets Operator or Sealed Secrets; `values-review`
  learns to flag plaintext secrets and recommend the secret store.

## Open questions / assumptions

- **values-review rubric:** assumed Claude best-practice defaults, editable in the
  skill. If the user has an internal standards doc, fold it in.
- **Argo CD chart:** `argo/argo-cd` upstream Helm chart, latest stable, pinned in
  `bootstrap/install.sh`.
- **GitOps repo name / location:** decided when the plugin runs `/argocd-init-repo`
  (likely a refactor of `data-platform-k8s-configs`).
- `gh` auth is done by the user out of band before Git-touching commands run.

## Risks

- Plugin command output must match the user's hand-written style closely enough to
  trust — mitigated by `argocd-repo-conventions` skill + `templates/` and by
  reviewing generated files against the existing repo during Phase 1.
- Live troubleshooting quality depends on cluster access + `argocd`/`kubectl`
  being configured in the session; offline mode is the fallback.
- Multi-source Application manifests with `$values` require Argo CD ≥ 2.6; note
  the minimum version in the conventions skill.
